# Runs, handles and background work

How a run is identified, how it survives resumes and forks, when it is handed off, and how the host manages one that runs in the background.

## Runs and handles

Every call to `claude` belongs to a run, and every run has a handle such as `run-3`: one more than the highest handle on the host's current branch. A run is an ordinary Claude Code session. After each call the extension records a `pi-fusion` custom entry in the host session with the handle, the role, the Claude Code session id, the host session id, and a checkpoint: the uuid of the child's last assistant message in that call. The last entry for a handle on the host's current branch is the run's state.

`continue` with a handle resumes that run's session at its checkpoint and sends `task`, and `context` if given, as the next user message. The run keeps its role; a `role` that differs from it fails the call. `model` and `effort` apply to the continued call as they do to a new one. Without `continue`, `implement` and `ultracode` start a new run, and `plan` continues the plan run with the last entry on the branch, so follow-ups can refer to the earlier agreement. `plan` with `fresh: true` starts a new plan run, and `continue` with the handle of an older plan run goes back to it. A `plan` call that would continue a run whose context has grown past its cap starts a fresh plan run instead (see [The context cap](#the-context-cap)).

Resuming the host session resumes its runs, because the entries are in the host's transcript. Going back with `/tree` takes the runs back too: the last entry on the older branch has an older checkpoint, and Claude Code continues from that message on a new branch of the child's transcript, leaving the abandoned turns in the file but out of context.

A call that fails after it resumed a session records nothing, so the next `continue` starts from the last successful call. A new run that fails before Claude Code reports its session records its handle with no session, so the handle is not given out again, and the next `continue` of it starts a new session. An entry without a checkpoint resumes the whole session.

A forked host session has a different session id from the one in the entry. The first `continue` of a run in the fork, or the first `plan` call for the plan run, resumes the recorded session with `--fork-session` at the recorded checkpoint into a new id and records that under the same handle, so the fork starts from a copy of the child's context up to that point and the two hosts stop sharing it from there on. A failed fork is recorded with the checkpoint it forked at. This covers both an in-session fork and `pi --fork <session>`. Nothing is copied at fork time; the fork happens on first use.

Entries written before handles existed carry only the plan session, under `consolidator` keys with a generation counter. The extension reads generation `g` as a `plan` run with handle `run-<g+1>`, so host sessions from before the change keep their plan session. A host started with `--no-session` keeps its entries in memory, so its runs last as long as the host does, but the Claude Code transcripts stay on disk like any other.

Claude Code stores the transcripts under `~/.claude/projects/<encoded working directory>/<session id>.jsonl`. If a recorded session has been deleted, or its checkpoint is no longer in the transcript, the next call to that run fails with Claude Code's error naming the session id or the message uuid; start a new run, or call `plan` with `fresh: true`.
A continued `ask` run keeps its mode unless the call names another.

## Aborting a run

Aborting a foreground call with Esc sends SIGTERM to the child's process group and to the process group of every descendant, then SIGKILL 5 s later to whatever is left, so a Bash command the child started dies with it. The extension spawns the child itself, through the SDK's spawn hook, because the SDK's own shutdown signals the child alone, 2 s after an abort, and escalates to SIGKILL only 5 s after that. The tool then fails with `<role> aborted while <activity>`. A child that has finished its turn but is still running 2 s after the SDK is done with it is stopped the same way; that stop is not reported as a failure.

## The context cap

A run that a host continues call after call keeps everything it read on the way, and that context is what each later call pays for. So each entry also records what the call's last model turn filled: the prompt tokens of that turn and the window they went into. Every call that would continue a run reads those from the last entry on the branch and compares them against a cap, 35% of the window by default. A `plan` call the host did not ask for by handle is the one case the extension acts on by itself: at or over the cap it starts a fresh plan run instead of continuing the old one.

The fresh run takes the next handle and gets the host's task with one section added: the replaced run's last report, capped at 32 KiB, between markers of its own, named as the plan agreed so far and marked as quoted data rather than instructions. What the run carries is the agreement, not the reading and the reasoning that reached it. The tool result opens with a line naming both handles and the share the old run had reached, so the host knows which run holds the plan now and that it can go back to the old one with `continue`. Later `plan` calls continue the fresh run, because its entry is now the last plan entry on the branch.

The handoff needs the replaced run's report, which it takes from this Pi process, or from the history when `PI_FUSION_HISTORY=1` kept it. When neither holds it, which is what a Pi restart without the history leaves, the call fails and says to restate the agreed plan in a `fresh: true` call or to continue the old run by handle. Nothing is handed off silently without the plan.

A `continue` call is never handed off. `fresh: true` is unaffected, because it starts a new run anyway: the host named the handle, and a run it names is the run it gets, however large that run's context has grown. Past the cap the call still runs and its result opens with a line that names the fill and what a fresh run would take instead: for `implement` and `ultracode`, a self-contained brief, because the work so far is in the work tree and the run's report names what it changed; for `plan`, a `fresh: true` call restating the agreed plan; for `ask`, a new `ask` run, which reads what it needs itself. The host decides. The extension does not refuse a `continue`, because `fresh` cannot go with `continue` and a refusal would leave a half-finished thread with no way to finish it in that session.

`PI_FUSION_PLAN_CONTEXT_PCT` sets the share, as a percentage between 0 and 100; `0` turns both off: every `plan` call continues the run as before, and no call warns about a context. It is read when Pi loads the extension, and a value that is not a percentage in that range leaves the default in place and says so once, the way the budget variables do.

The context fill is also shown where a run's numbers are: `context 400.0k/1.00M (40%)` in the stats line of every call that reported one, and `context 40%` in `/fusion status` and `claude_control status`. A share that rounds to zero reads as `<1%`.
## Background runs

`background: true` works for every role. The call returns `<handle> started in the background; you get the report when it ends`, and the host can go on talking with the user. When the run ends, the extension sends the host a `pi-fusion-run` message with the handle, the final state, the report or the failure message, and the stats line. It calls `pi.sendMessage` with `triggerTurn: true` and `deliverAs: "followUp"`: Pi starts a new turn when the host is idle and queues the message as a follow-up when the host is in a turn. A run whose report reached the host through `claude_control wait`, and a run `claude_control cancel` stopped, send no message. A run the user cancels with `/fusion cancel` does send one, so the host hears about an end it did not order.

At most one run that is not an `ask` run is active at a time, foreground or background. A call to `claude` that would start or continue a second one fails with an error that names the active handle. `ask` runs can be active next to it, because they do not change files. Continuing a run that is still active fails with an error that points to `claude_control message`.

Esc stops a foreground run, as before, but not a background run. `claude_control cancel` and `/fusion cancel` stop a background run the same way, and so does the end of the host session: quit, `/reload`, `/new`, `/resume` and `/fork` stop every active run before Pi tears the extension down. They also wait for a run that has ended but is still writing its entry, so the run keeps its handle and session in the host session. A new handle skips every handle this Pi process has used, so a run on one branch never takes the handle of a run that another branch still shows.

`/tree` is refused while any run is active, `waiting` and `ask` runs included, because the run's report and its `pi-fusion` entry would land on the destination branch. The refusal lasts until each run's `pi-fusion` entry is recorded and its report is delivered, which happens a moment after the run's state turns final, while the extension takes the last git snapshot. The extension shows a warning that names each such handle and role, marks a run whose state is final but whose entry or report is still pending as `finishing`, and cancels no run. Wait for the runs or cancel them with `claude_control`, then run `/tree` again.

`claude_control` takes `action`, `run` (a handle) and `message`:

- `status` without `run` lists every run of this Pi session with handle, role, model, state, elapsed time and open question. With `run` it adds the current activity, the tool call count and, for a run that is not an `ask` run, the files that changed in the work tree so far. It never returns the report.
- `wait` blocks until the run ends and returns its report or failure message, or until it asks a question and returns the question. Esc stops the wait; the run goes on.
- `message` answers a waiting run's question, or sends a steer to a running child. The extension gives the SDK a queue of user messages as the child's input, not a single prompt, so stdin stays open while the child can still take a turn; it closes when a turn ends with no background task left. Claude Code reads the steer when it next takes input. A message to a run that has ended sends nothing and is not an error, because a steer can race the run's end: the result gives the run's final state and a summary of its report, and says the host can continue the run with `claude` and `continue`, or take no action.
- `cancel` stops the run and marks it `cancelled`.

The user has the same controls without the host: `/fusion status`, `cancel`, `steer`, `wait`, `answer` and `review` act on the same runs (see [The /fusion command](fusion-command.md)). Each form that changes a run tells the host what the user did.
## Runs across Pi processes

The runs live in the Pi process. A run recorded on the branch by an earlier Pi process is not active; `claude_control` says so, and `claude` with `continue` continues it.

With `PI_FUSION_HISTORY=1` the extension also keeps the runs of each durable Pi session on disk, so a later Pi process on that session can show them. The extension writes a run when it starts, when its token count changes and when it ends, so a Pi process that dies mid-run loses little of it.

This writes project content to disk. When `PI_FUSION_HISTORY=1` is set, every run's prompt, report, failure text, changed-file paths and Claude Code session id are written under the history directory, which is `pi-fusion/history` under `~/.pi/agent`, or under `PI_CODING_AGENT_DIR` when that is set, or the directory `PI_FUSION_HISTORY_DIR` names. The directory is mode 0700 and each file mode 0600, one JSON file per Pi session, at most 100 records per file, 200 files and 1 MiB per file, with the oldest going first. They stay until you delete them, or until a cap drops the oldest to make room. Nothing is written while the variable is unset, and nothing is written for a Pi session that keeps no file of its own, such as a host started with `--no-session`. Texts are bounded: the prompt and the report at 32 KiB each, a failure at 4 KiB, and 500 changed paths per run. A run whose record alone would pass the 1 MiB file budget keeps its counts and gives up its path list, so one run never costs the file.

A later Pi process on the same session reads that file and shows what it finds. `/fusion status` lists each earlier run under the live ones as `run-1 · implement · opus · done · earlier Pi process`. `/fusion status run-1` and `claude_control status` with that handle give `run-1 (implement) ran in an earlier Pi process: done, 42s, 3 changed files`, the first 600 characters of its report or failure, and the lines that say to continue it with `claude` and `continue run-1` and to review it with `/fusion review run-1`, each shown when that is possible: continuing needs the run's session on the host branch, and a review needs a run this working directory made. The session cost starts from what those runs spent, the dashboard lists them as restored, and a new handle never reuses an earlier process's. A run that was still going when its Pi process ended comes back as `aborted`. A forked host reads its ancestor session's file and never writes to it.

The files are written through a temporary file and a rename, and are never followed through a symbolic link. A file this pi-fusion cannot read costs one warning and never a run: a corrupt or foreign file is replaced by the next write, a file a newer pi-fusion wrote is left alone and read by nobody, and any other trouble, such as a directory this extension cannot make private, is reported once per Pi process and then kept quiet.
